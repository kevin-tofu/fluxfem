[Contact Progress Note 2]

現状、CoupledSystem と contact tutorial にはハードコーディングが多い。
理由は「まず Nitsche で解ける最短経路」を優先したため。

主な要因
1) DOF マッピングの手動指定
- `n_master_nodes`, `n_slave_nodes`, `master_offset`, `slave_offset` を呼び出し側で直指定している。
- 本来は FESpace / ContactSpace から自動構築すべき。

2) Interface DOF ordering 前提
- `J_contact` / `residual` は `[master, slave]` 順序を前提にリフトしている。
- 一般化するには field name と local-to-global map の明示管理が必要。

3) Stabilization/penalty の固定値
- tutorial 側で `alpha`, `inv_h`, `diagonal_shift` を固定している。
- 問題依存で最適値が変わるため、設定オブジェクト化が必要。

次の改善方針
A) `CoupledSystemBuilder`（仮）導入
- `from_spaces(...)` で構造 DOF map を自動生成。
- `add_contact(...)` で mortar/nitsche を統一 API で追加。

B) Contact parameter の dataclass 化
- `ContactParams(alpha, inv_h, rho, diagonal_shift, active_set_opts, ...)`。
- tutorial/テストから魔法定数を削減。

C) Ordering 契約の明文化
- interface block の field ordering を API 契約として定義。
- 必要なら permutation を builder 内で自動適用。

D) Active-set（将来）
- 研究要素として optional 実装。
- まずは linearized Nitsche path を安定化してから段階導入。

補足
- 現在の実装は「動く最小系」であり、設計的には過渡状態。
- 次フェーズで builder + params へ整理して、ハードコード依存を減らす。

[2026-03-07 design direction (law/enforcement split)]
- 目的
  - 接触の物理定義（片側、法線のみ、摩擦あり等）と、
    数値拘束の組み立て方式（Nitsche/Mortar）を分離する。
  - 利用者は「何を解くか（law）」と「どう課すか（enforcement）」を独立に選べる。

- 設計原則
1) Contact law を先に定義
  - 例: one-sided + normal-only, Coulomb friction, stick/slip など。
  - law は traction/gap/effective tangent の評価責務を持つ。

2) Enforcement は build 時に選択
  - `builder.add_contact(..., method=\"nitsche\"|\"mortar\")` で決定。
  - 同一 law を Nitsche/Mortar の両方で比較可能にする。

3) Builder が組み立て詳細を吸収
  - Mortar: coupling から KKT 生成 (`assemble_contact_kkt`) は builder 内部で実施。
  - Nitsche: residual/jacobian 生成は builder 側で統一入口から委譲。
  - 呼び出し側が `ops.coupling_aa/ab` などの内部表現を直接扱う箇所を減らす。

- API 方針（後方互換を維持）
  - `method` は当面維持しつつ意味を enforcement として文書化。
  - 将来的に `enforcement` 引数を正式化し、`method` は alias 扱いへ移行。
  - `contact law` を外部注入可能にする引数（`law` など）を `assemble_contact_operators` /
    `builder.add_contact` 側で受けられるようにする。

- デフォルト接触（アプリ向け）
  - 初学者/アプリ用途向けに、最小構成の default law を提供する。
  - 初期案:
    - `default_contact_law = one_sided + normal_only + frictionless`
    - 安定化の初期パラメータ（alpha/rho など）を conservatively 設定
  - README/usage には「デフォルトでまず動かす経路」と「law を差し替える経路」を併記。

- 実装ステップ（次フェーズ）
A) 契約整理
  - ContactLaw の最小インターフェース定義（評価に必要な関数群）。
  - interface ordering 契約を builder 側に閉じ込める（呼び出し側へ露出しない）。

B) Builder 統合
  - `add_contact(...)` で `law` + `method(enforcement)` を受ける。
  - Mortar/Nitsche 分岐を内部化し、手動 `assemble_contact_kkt` 呼び出しを不要化。

C) ドキュメント更新
  - README の contact 例は builder 主体に寄せる。
  - 低レベル API（coupling 行列直操作）は「advanced」節に退避。

D) 回帰テスト
  - 同一 law を Nitsche/Mortar で通す API レベル整合テスト。
  - default law の smoke test（one-sided/normal-only/frictionless）。
